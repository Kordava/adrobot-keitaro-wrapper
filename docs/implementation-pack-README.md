# Adrobot — пакет для ИИ-реализации

Версия пакета 0.1 · 19 ноября 2026 г. · Действующее ТЗ: **v0.3.1 с исправленной фразой DoD**

## Назначение

Пакет переводит принятое ТЗ в связанные рабочие записи: правило → исходный раздел → критерий приёмки → задача. Он помогает исполнителю брать нужный контекст для текущей работы, сохранять выбранный объём и видеть реальные зависимости от API.

Исходное ТЗ сохранено целиком и без изменений. В YAML извлечено 70 правил; 37 критериев приёмки и весь DoD перенесены дословно. План содержит пять задач из §15. Состав продукта, инженерная планка и поведение редактора сохраняются.

**Статус:** пакет готов для начала разработки и исследования инстанса. Реализация приложения и фактическая интеграция этим пакетом не подтверждены. OPEN-01…06 остаются непроверенными фактами Keitaro, OPEN-07 — организационным вопросом.

## Как использовать с ИИ

Для старта достаточно дать ИИ эту папку и следующий запрос:

> Работай по AGENTS.md и активному ТЗ из 00_manifest.yaml. Начни с TASK-01 из 04_tasks.yaml. Используй связанные правила и точные AC; сохраняй принятый объём и ENG baseline. Сначала выполни доступную независимую часть. Фактические Keitaro endpoints и payload подтверждай документацией и тестовым инстансом, результаты записывай в docs/keitaro-api-notes.md. Если доступа ещё нет, укажи конкретную незавершённую интеграцию и продолжай каркас, чистый domain и подходящие fake-тесты. Не объявляй mock-проверку доказательством реальной интеграции.

При переходе к следующей задаче читать её запись, указанные rule_refs, acceptance_refs и соответствующие разделы исходного ТЗ. Правила SCP относятся ко всему проекту. Исторический архив открывать для вопроса о происхождении требования или сверки с видео/PDF; старые ТЗ внутри него не становятся действующими инструкциями.

AGENTS.md рассчитан на рабочую папку проекта. Если репозиторий уже содержит свои инструкции, сохранять их применимые требования при размещении этого пакета; пользовательские указания остаются приоритетными.

## Что можно делать сейчас

- Каркас FastAPI, конфигурацию без секретов, управление ресурсами, обработку ошибок и tooling/CI.
- Чистую Python-функцию двух режимов и проверки принятой математики на внутренних данных.
- Внутренний Preview, UI черновика, оркестрацию и тесты с подставной инфраструктурой.
- Read-only исследование Keitaro, когда доступен тестовый инстанс.

Окончательный ключ архива зависит от OPEN-03. Реальные чтение и запись долей зависят от подтверждённого mapping OPEN-02. Создание требует фактической схемы OPEN-01 и defaults OPEN-05; безопасный update — OPEN-06. Подробные моменты применения указаны в 03_api_discovery.yaml.

Эти зависимости не превращают пять задач в строгую последовательность заблокированных этапов. Например, чистый расчёт §6 можно начать одновременно с API-исследованием, а создание и независимые части редактора могут развиваться параллельно после появления основы проекта.

## Несколько правил, которые особенно легко потерять

- Fetch/readback сохраняет считанные доли, включая 25/25; нормализация чтения запрещена.
- В RECALCULATED Unpin сразу обновляет Preview. Полный возврат к базе сравнивает **порядок активных привязок и все Pin**, включая архив.
- pinned_shares — полный набор закреплений, а не patch. Пропущенный ключ снимает Pin; пропущенное целиком поле — ошибка.
- Push использует ту же чистую функцию, реальные перечитанные базы и обе ревизии; состояние актуального Preview контролирует UI.
- Удалённая привязка остаётся в локальном архиве после Push и после внешнего удаления. Глобальный Offer не удаляется.
- UNKNOWN, PARTIAL, CONFLICT и неподтверждённый readback не становятся SUCCESS. Автоматического слепого повтора мутации нет.

Эти пункты приведены для навигации; точные действующие формулировки находятся в ТЗ и связанных правилах.

## Приёмка и доказательства

Один AC может включать несколько стадий и проверяться в разных задачах. Например, AC-E-13 содержит расчёт и последующий Push: одного domain-теста недостаточно, чтобы объявить весь сценарий выполненным. Количество тестов определяется содержанием сценария; создавать по одному тесту на каждую YAML-запись не требуется.

Правила без отдельного AC не становятся необязательными: часть инженерных условий проверяется обзором кода, README и DoD. Критерии не увеличены; готовность приложения определяется исходными 37 AC и DoD.

Для API нужен один актуальный `docs/keitaro-api-notes.md`, который создаётся во время исследования. В нём различать факты документации, подтверждённое чтение и подтверждённую мутацию/readback. В пакет не внесены предполагаемые upstream endpoints или payload.

## Проверка самого пакета

Нужны Python 3 и PyYAML. Из корня папки:

```bash
python checks/validate_pack.py --output checks/validation.json
```

Проверяются SHA256 ТЗ и исторического архива, индекс разделов, существование всех ссылок, покрытие явных REQ/C/E-ID, точное совпадение 37 AC и DoD с исходником, таблица внутренних маршрутов и зависимости пяти задач.

Это структурная проверка документации. Она не доказывает правильность всего кода, поведение живого API или прохождение приёмки приложения.

## Обновление

При изменении ТЗ сохранять одно явно выбранное действующее основание. Исправления производных YAML сверять с этим основанием; не редактировать AC отдельным новым пересказом. Если API-факт требует минимальной корректировки выбранного решения, записать факт и причину изменения, сохранив границы задачи.

Отдельные Contract/Proposal для каждой задачи, система согласований, журнал распределённых операций и новые инфраструктурные компоненты этим пакетом не вводятся.
