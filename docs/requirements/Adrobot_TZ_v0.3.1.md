# Adrobot — техническое задание

**Версия:** 0.3.1 — точечная коррекция контракта Preview / Pin / Push после сверки v0.3  
**Дата:** 19 ноября 2026 г.  
**Проект:** финальное тестовое задание для «Это Легко»  
**Статус:** внутренний функциональный и инженерный baseline с согласованной семантикой черновика; контракт конкретной версии Keitaro Admin API пока требует подтверждения  
**Срок:** 5 дней согласно сообщению в HR-анкете; начало отсчёта уточняется отдельно  
**Обязательный стек заказчика:** FastAPI + SQLAlchemy, фронтенд по выбору  
**Формат сдачи:** ссылка на доступный проверяющим GitHub-репозиторий, README с инструкциями по запуску и миграциям

> **Главный принцип.** Воспроизвести **логику** существующего редактора, показанную заказчиком, и реализовать создатель кампаний. При этом сделать компактный, грамотно спроектированный сервис: чёткие границы ответственности, типизация, содержательные docstrings, тестирование, pre-commit, CI, безопасная интеграция и диагностируемые ошибки. Не превращать тестовое в платформу с ненужными абстракциями и недоказанными гарантиями.

### 0.2. Классы требований

- **REQ** — прямо требуется письменным заданием заказчика.
- **DEMO-REQ** — существенное поведение, показанное/проговорённое в S2; **обязательно**, поскольку S1 требует «воспроизвести эту логику». Свобода выбора относится к внешнему виду интерфейса.
- **ENG** — наш обязательный внутренний инженерный стандарт, мотивированный S4 и выбранной планкой качества; не выдавать за прямое пожелание заказчика.
- **DESIGN** — конкретное минимальное решение там, где исходные материалы оставили выбор; считается принятым для v0.3.1, если не помечено `OPEN`.
- **OPEN** — деталь, ещё не подтверждённая фактическими ответами API либо источниками. Блокирует лишь затрагиваемый участок реализации, не весь проект.

**Приоритет:** точные требования S1 → бизнес-поведение S2 → подтверждённая семантика API → наши DESIGN/ENG. Ни одно инженерное решение не должно менять показанную продуктовую логику.

### 0.3. Что изменилось относительно v0.2

1. Восстановление `Bring Back` работает **после Push**, а не только в черновике.
2. `Fetch` синхронизирует ранее известные привязки и фиксирует **внешние удаления** из Keitaro.
3. `Pin/Unpin` включены в основную логику; закреплённые целые проценты сохраняются при перераспределении.
4. **Чтение значений** отделено от **пересчёта**: `Fetch` не нормализует `25/25` в `50/50`.
5. SQLAlchemy хранит **известные привязки/архив и настройки Pin**, а не обязательную систему управления распределёнными операциями.
6. Установлен один путь математического расчёта: Python domain + серверный `Preview`; JavaScript не дублирует формулы.
7. Удалены обязательные универсальные `Idempotency-Key`, восемь состояний журнала, восстановление «после рестарта», жёсткий порог покрытия, обязательные ADR/множество отдельных архитектурных документов и обязательный Docker Compose.
8. Сохранены и усилены тестируемые требования к архитектуре, ошибкам, логированию, миграциям, типизации, docstrings, pre-commit и CI.
9. Исправлены несогласованности статусов `OPEN`, `base_revision`, документации и состава сдачи.

### 0.4. Уточнение v0.3.1 по результатам проверки v0.3

1. В черновике определены два явных режима: `SNAPSHOT` (показывать считанные доли без нормализации) и `RECALCULATED` (вычислять доли для текущего состава и Pin).
2. `Pin/Unpin` в `RECALCULATED` сразу приводит к новому Preview; полный возврат **состава и Pin** к базе имеет приоритет и восстанавливает исходный snapshot. Сценарии с одинаковыми финальными входными данными больше не зависят скрыто от порядка нажатий.
3. `Preview` и `Push` используют один чистый Python-контракт, включая режим и базовые Pin. Оговорены атомарность UI-состояния, актуальность Preview и согласование локальной версии Pin.
4. Уточнены примеры HTTP-контракта, критерии AC-E-04/13/19/20, проверка OPEN-01…06, маршрут JSON-Fetch и единый инструмент type checking (`mypy`).

## 1. Цель, результат и границы задачи

**REQ-01.** Разработать небольшое веб-приложение — обёртку над Keitaro, выполняющее две самостоятельные функции:

1. **Создатель кампаний:** по имени, GEO и существующему ID оффера создаёт кампанию с двумя потоками и заданными доменом, группой и источником.
2. **Редактор кампаний:** загружает существующие потоки, изменяет состав офферов, показывает корректные доли, сохраняет изменения в Keitaro и воспроизводит историю/закрепление из видео.

**REQ-02.** Результат должен реально изменять **тестовый** Keitaro, а не демонстрировать мокированные данные. Моки допустимы в автоматических тестах.

**REQ-03.** Веб-интерфейс произвольного вида, но все представленные действия функциональны; значения и статусы не подделаны.

### 1.1. Вне объёма

- Создание/удаление глобальных `Offer` в Keitaro; создание лендингов и партнёрских сетей.
- Настройка Meta/Facebook, рекламные кабинеты, обход модерации, аналитика рекламных кампаний.
- Полноценная CRM, поиск кампаний по десяткам фильтров, управление пользователями и ролями.
- Отдельная страница архива, полноценное редактирование произвольных процентов, графики `Stats/Trends` без реальных данных.
- Микросервисы, брокеры очередей, Redis/Celery, Kubernetes, production-scale инфраструктура.
- Автоматический откат удалённых сущностей или гарантированная распределённая транзакция с Keitaro.

### 1.2. Критерий достаточности

Две функции из REQ-01 проверяемо работают; демонстрационная бизнес-логика из §4–6 воспроизведена; основной happy path и характерные отказы покрыты тестами; проект запускается из чистого клона по README. Дополнительный UI и инфраструктура не должны задерживать эти результаты.

## 2. Модель предметной области и источники истины

| Понятие | Смысл |
|---|---|
| `Campaign` | Кампания Keitaro, у которой есть ID, домен, группа, источник и потоки |
| `Stream` / `Flow` | Поток Keitaro; может содержать офферы либо выполнять другое действие, например redirect |
| `Offer` | Глобальная уже существующая сущность Keitaro с ID |
| `Offer binding` | **Привязка** оффера к конкретному потоку; именно её создаёт/убирает редактор |
| `Active` | Привязка присутствует в текущей конфигурации Keitaro либо включена в редактируемый черновик |
| `Removed` | Привязка была известна Adrobot, но сейчас отсутствует в Keitaro или помечена к удалению в черновике |
| `Displayed share` | Целочисленная доля, показанная пользователю; её связь с полями Keitaro устанавливается API mapping |
| `Pinned share` | Локальная настройка Adrobot, фиксирующая долю конкретной активной привязки при следующем перераспределении |
| `Snapshot` | Последнее успешно прочитанное и валидированное состояние Keitaro для данного потока **и базовые локальные Pin** на момент Fetch/подтверждённого Push |
| `Draft` | Неопубликованные изменения относительно snapshot, в том числе добавление/удаление/восстановление/Pin |
| `Draft mode` | `SNAPSHOT` — показывать считанные доли; `RECALCULATED` — пересчитать по текущему составу и Pin |
| `base_pin_revision` | Отпечаток базового набора ранее известных привязок и их Pin, используемый для best-effort сверки локальных настроек при Push |

**Разграничение ответственности (DESIGN):**

- Keitaro — источник истины **о текущем удалённом составе потоков и их сохранённых долях**.
- Локальная SQLAlchemy-БД — источник истины **о ранее известных Adrobot привязках, их архивных именах и настройках Pin**.
- Браузер — временное хранение черновика, не отдельный постоянный источник данных. После закрытия/перезагрузки страницы неопубликованные изменения могут быть потеряны с предупреждением.
- Нельзя считать отсутствующую в очередном *неуспешном* ответе Keitaro привязку удалённой.
- `Remove` никогда не вызывает удаление глобального `Offer`.

## 3. Часть I. Создание кампании

### 3.1. Вход и интерфейс

| ID | Класс | Требование |
|---|---|---|
| C-01 | REQ | Обязательное непустое `Name` — имя кампании |
| C-02 | REQ | Обязательное `Geo` — код страны для первого потока |
| C-03 | REQ | Обязательный `Offer ID` существующего оффера |
| C-04 | DESIGN, по примеру S3 | Принимать одиночный ISO country code либо несколько через запятую (`AU`, `MX,AU,RO`), нормализовать пробелы/регистр, убрать повторы; строгую семантику списка проверить в Keitaro |
| C-05 | DESIGN, по примеру S3 | Поиск существующего оффера по ID/названию с автодополнением; выбор возвращает действительный ID |
| C-06 | REQ | Домен, группа и источник кампании должны быть настроены через Keitaro API |
| C-07 | DESIGN | Домен, группа и источник берутся из валидируемых конфигурируемых defaults; полноценные селекты необязательны |
| C-08 | ENG | Входные значения валидируются сервером до мутаций; ошибки объясняются пользователю |

Скриншотный образец `in.posdk.xyz`, `FORTESTS`, CPC/стоимость/UTM — **не универсальные обязательные константы**. В `env` хранятся ID/имена defaults, найденные в тестовом инстансе; при их отсутствии создание не выполняется с понятной ошибкой. Никакого создания новых групп/источников «на лету» не требуется.

### 3.2. Созданная конфигурация

| ID | Класс | Требование |
|---|---|---|
| C-09 | REQ | Ровно **два** потока целевой кампании |
| C-10 | REQ | **Первый по приоритету** поток принимает указанные GEO и направляет на `https://google.com` |
| C-11 | REQ | **Второй поток** направляет трафик, не перехваченный первым, на выбранный Offer ID |
| C-12 | REQ | Домен, группа и источник относятся именно к созданной кампании |
| C-13 | DEMO-REQ/фактический образец | Для схемы используется **позиционный** порядок обработки потоков, GEO-поток выше офферного |
| C-14 | DESIGN | Выбранный оффер присутствует в fallback-потоке в единственном экземпляре |
| C-15 | ENG | После создания прочитать кампанию и потоки обратно и проверить ID, настройки и порядок |

Конкретные типы потоков, поля фильтров, alias, режим redirect и формат назначения оффера **не придумывать**. Они определяются по фактической версии Keitaro в §9 и фиксируются в коротком API mapping до live-теста.

### 3.3. Ход создания

1. Проверить имя, GEO, существование оффера, доступность домена/группы/источника.
2. Создать кампанию с установленными обязательными атрибутами.
3. Создать/настроить GEO-поток → Google.
4. Создать/настроить fallback-поток → выбранный оффер.
5. Установить/проверить порядок потоков.
6. Прочитать фактическое состояние из Keitaro.
7. Только после совпадения с ожидаемым состоянием показать `SUCCESS` с ID и ссылкой на кампанию.

**При частичном успехе:** если кампания/часть потоков созданы, показать известный `campaign_id` и последний подтверждённый этап, `PARTIAL`. Автоматически не удалять созданное и не повторять весь сценарий. Для сохранности при перезапуске журнала операций **не требуется**; сервер записывает диагностический лог, а UI получает доступные сведения из результата.

**При потере ответа на create:** исход `UNKNOWN`, если нельзя доказать отсутствие записи; автоматического второго `POST` нет. `operation_id` сам по себе не гарантирует дедупликацию в Keitaro. Пользователь получает инструкцию проверить Keitaro перед новой попыткой.

## 4. Часть II. Редактор — функциональный контракт

### 4.1. Загрузка и отображение

| ID | Класс | Требование |
|---|---|---|
| E-01 | REQ | Открыть существующую кампанию (достаточно ввода `campaign_id`) |
| E-02 | DEMO-REQ | Кнопка `Fetch streams from KT` читает и отображает потоки кампании |
| E-03 | DEMO-REQ | Для офферных потоков отображаются ID, имя, доля и состояние каждого известного оффера |
| E-04 | DEMO-REQ | Неофферные потоки тоже отображаются **как потоки**, но без необходимости парсить и выводить их фильтры/URL/redirect |
| E-05 | DEMO-REQ | Поиск существующего оффера по Keitaro и действие `Add` в целевой офферный поток |
| E-06 | DEMO-REQ | `Remove`, `Bring Back`, `Push to KT`, `Cancel`, повторный `Fetch` |
| E-07 | DEMO-REQ | `Pin` закрепляет текущую целочисленную отображаемую долю; возможность `Unpin` — наше небольшое DESIGN-решение |
| E-08 | DESIGN | Ссылка `View in KT` открывает конкретную кампанию в админке |
| E-09 | DESIGN | Наличие черновика заметно: `DIRTY`/выделение потока, кнопки публикации и отмены |
| E-10 | ENG | Ошибки чтения/записи явно видны; не подменяются пустыми таблицами и HTTP 200 |

**Примечание об офферных потоках:** поток, из которого *внешне удалены все офферы*, всё равно должен показывать локальный архив и `Bring Back`, если Adrobot знает этот поток. Наличие пустого текущего списка само по себе не означает, что поток перестал быть редактируемым. При отсутствии истории определение его типа выполняется по минимальным полям API, без разбора URL и фильтров редиректа.

### 4.2. Добавление (`Add`)

1. Пользователь выбирает действительный существующий оффер в определённый поток.
2. Оффер появляется **в черновике**, но не в Keitaro.
3. Доли активных офферов пересчитываются по §6; поток становится `DIRTY`.
4. `Push` отправляет результат в Keitaro, проверяет чтением и делает черновик `CLEAN`.
5. Добавить тот же `offer_id` второй раз в тот же поток нельзя; для другой привязки с тем же ID устанавливается отдельное правило только если API подтвердит такую модель (OPEN-03).

### 4.3. Удаление (`Remove`)

1. `Remove` исключает привязку из активного состава черновика.
2. Строка остаётся в интерфейсе серой/приглушённой со статусом `Removed`, `0%`, действием `Bring Back`.
3. Остальные активные доли перераспределяются сразу в черновике, **до** `Push`.
4. `Push` убирает **привязку** из целевого потока Keitaro, не удаляя Offer как глобальный объект.
5. **После успешного Push строка остаётся в архиве Adrobot** и по-прежнему может быть восстановлена.

### 4.4. Восстановление (`Bring Back`)

- Доступно для удалённой записи **до публикации** и для **архивной** записи после опубликованного либо внешнего удаления.
- В черновике привязка вновь активна; действуют правила пересчёта §6; поток становится `DIRTY`.
- При `Push` привязка снова появляется в Keitaro и подтверждается readback.
- Если у архивной строки сохранён `pinned_share`, он учитывается при возврате в активный набор; если из-за него набор невозможен, `Preview` сообщает об ограничении и разрешает `Unpin`.
- Если исходный Offer ID больше не существует глобально в Keitaro, `Bring Back` не должен превращаться в фиктивный успех: показать ошибку валидации.

### 4.5. Отмена (`Cancel`)

- Восстановить последний успешный snapshot **вместе с локальными Pin-настройками на момент загрузки/последнего успешного Push**.
- Не выполнять write-запросов к Keitaro.
- Не сохранять новые, добавленные и затем отменённые офферы в архив `known_offer_bindings`.
- Сценарий из ролика: `4 × 25%` → `Add` пятого (`5 × 20%`) → `Cancel` → `4 × 25%`, пятый отсутствует в архиве.
- Если итоговый **упорядоченный** активный состав и **все** настройки Pin (включая архивные строки) снова совпадают с базовыми, система показывает **исходные считанные доли**, возвращается в режим `SNAPSHOT` и состояние `CLEAN`, даже если ранее был перерасчёт; ненужного Push нет.
- Одного возврата прежних IDs недостаточно для сброса перерасчёта, если итоговые Pin отличаются от базовых. `Cancel` всегда восстанавливает также режим `SNAPSHOT` и валидный базовый Preview.

### 4.6. Опубликованное и внешнее удаление

**DEMO-REQ — опубликованное удаление:**

```text
Fetch → Remove(A) → Push → Fetch
Keitaro: A отсутствует
Adrobot: A = Removed, 0%, Bring Back
Bring Back(A) → Push → Fetch
Keitaro: A снова присутствует
```

**DEMO-REQ — внешнее удаление:**

```text
Adrobot ранее видел A, B, C, D
Keitaro UI: вручную удалены C и D
Adrobot: Fetch
A, B: ACTIVE, с фактическими долями из Keitaro
C, D: REMOVED, 0%, доступны для Bring Back
```

Этого нельзя добиться хранением только текущего списка Keitaro: локальная история обязательна (§7).

### 4.7. Поведение `Fetch` при ошибках

- Синхронизация выполняется **только после успешного полного чтения** нужных потоков/всех страниц выдачи и валидации схем.
- Частичный/неполный ответ API, таймаут, `401`, `5xx`, невалидный JSON **не превращают ранее известные привязки в Removed** и не перезаписывают локальный архив ошибочными данными.
- Если пользователь изменил черновик, повторный `Fetch` требует явного подтверждения его сброса. Тихо терять изменения нельзя.
- Неофферный поток при Fetch не требует отображения подробностей redirect/filter, но не должен быть изменён.

## 5. Жизненный цикл черновика и публикации

```text
NOT_LOADED
    │ успешный Fetch (полный read + локальная синхронизация)
    ▼
CLEAN / SNAPSHOT
    │ Add / Remove / Bring Back / Pin / Unpin
    ▼
DIRTY / SNAPSHOT либо DIRTY / RECALCULATED
    │   │
    │   ├─ Preview (чистая Python domain-функция; без записи)
    │   ├─ Cancel → CLEAN / SNAPSHOT
    │   ├─ полный возврат base IDs + base Pins → CLEAN / SNAPSHOT
    │   └─ валидный актуальный Preview → Push → SAVING
    │                                             │
    │                                     remote write/readback (если нужен)
    │                                     + локальная синхронизация/Pin commit
    │                                             ▼
    └──────────────────────────────────────── CLEAN / SNAPSHOT

SAVING → FAILED / UNKNOWN / CONFLICT (понятная ошибка, черновик не теряется)
```

- `Fetch` возвращает последнее **фактическое** состояние Keitaro и базовые локальные Pin; стартовый режим — `SNAPSHOT`, состояние — `CLEAN`.
- `DIRTY` определяется сравнением **итоговых** упорядоченных активных привязок и полного набора Pin с базой, а также режимом перерасчёта, когда он меняет опубликованные доли. Совпадение состава и базовых Pin всегда восстанавливает `CLEAN / SNAPSHOT`.
- `Pin/Unpin` в режиме `SNAPSHOT` меняет локальную настройку и оставляет считанные доли; в режиме `RECALCULATED` сразу запускает перерасчёт (см. §6). При изменении Pin без изменения remote-долей статус `DIRTY` сохраняется до подтверждённого локального Push.
- `Preview` изменяет **только временный черновик**: рассчитывает и валидирует состав, режим, Pin и отображаемые доли; не выполняет записей ни в Keitaro, ни в локальную БД.
- `Push` перед записью перечитывает Keitaro и локальные Pin, сверяет `base_revision` и `base_pin_revision`, воспроизводит Preview **той же чистой функцией** и только затем применяет изменения. Валидационный результат должен совпасть с последним актуальным Preview при неизменных базовых данных.
- Если отличаются только Pin, а целевой состав/доли Keitaro не меняются, `Push` обновляет **только локальные настройки**, без upstream `PUT`. Результат подтверждается чтением локальных настроек.
- `Cancel` восстанавливает базу, включая активный состав, считанные доли, архив, Pin и режим; серверного `Cancel` API нет.
- На время запроса Preview действия с тем же черновиком сериализованы, Push заблокирован до **актуального успешного** ответа. Неактуальный или ошибочный Preview не может разрешить Push (см. §8.2).
- На время `SAVING` повторное нажатие Push заблокировано; на сервере нет автоматического повтора неизвестной записи.
- После `CONFLICT` пользователь получает предложение `Fetch`, но черновик не удаляется без подтверждения.
- `FAILED`, `UNKNOWN`, `CONFLICT` — результаты команды, а не долговечный workflow-движок в БД.

## 6. Доли, Pin и правила расчёта

### 6.1. Два режима и переходы — нормативный DESIGN-контракт

| Режим | Назначение и вычисление |
|---|---|
| **`SNAPSHOT`** | После Fetch/readback показывает **буквально считанные доли** Keitaro, даже `25/25` (без нормализации). `Pin/Unpin` меняет только локальную настройку; доли не меняются. |
| **`RECALCULATED`** | Активные доли определяются **исключительно текущим упорядоченным составом и полным набором Pin** по §6.2. После принятого `Pin/Unpin` выполняется новый Preview, даже если состав не изменился. |

Переходы:

1. Успешный `Fetch` или подтверждённый `Push` фиксирует базовый **упорядоченный список активных привязок**, фактически прочитанные доли, известный архив, **полный базовый набор Pin**, `base_revision` и `base_pin_revision`. Черновик начинает в `SNAPSHOT / CLEAN`.
2. Принятое `Add / Remove / Bring Back`, **реально меняющее активный состав**, устанавливает `RECALCULATED`: сервер проверяет ограничения и применяет алгоритм §6.2. Отклонённое действие не меняет предыдущий валидный черновик, режим или доли.
3. `Pin/Unpin` в `SNAPSHOT` не пересчитывает считанные доли (в том числе `25/25`), но создаёт `DIRTY`, если Pin отличается от базовых. `Pin/Unpin` в `RECALCULATED` немедленно рассчитывает новые доли **по текущему составу и текущим Pin**; если действие невалидно, остаётся предыдущий валидный результат.
4. **Правило приоритета:** если итоговый **упорядоченный** активный состав и **весь** набор Pin вновь совпали с базовыми, независимо от истории действий восстановить исходные считанные доли, `SNAPSHOT / CLEAN`. Если совпали только IDs, но Pin изменены, оставаться в текущем режиме (в частности, `RECALCULATED` не превращается обратно в `SNAPSHOT`).
5. На любой стадии `Cancel` без сетевой записи восстанавливает исходный `SNAPSHOT / CLEAN`; успешный `Push` устанавливает новую базу **только после необходимого подтверждения** (§5, §7).

**Почему необходим режим.** Исходная база: `A=25, B=25`, сохранён `Pin(A=25)`, `C` в архиве. Тогда:

| Последовательность | Актуальный Preview перед Push |
|---|---|
| `Unpin(A) → Bring Back(C)` | `A=34, B=33, C=33` |
| `Bring Back(C) → Unpin(A)` | `A=34, B=33, C=33` |

В обоих случаях состав `[A,B,C]`, итоговый Pin `{}` и режим `RECALCULATED`, поэтому серверный Push рассчитывает те же значения. Устаревший результат `25/38/37` после `Unpin` **запрещён**.

**Контрпример к сравнению только IDs.** Начало: `A=25, B=25`, Pin отсутствуют, `C` в архиве. `Bring Back(C)` даёт `34/33/33`; `Pin(A=34)` фиксирует долю; `Remove(C)` возвращает прежний активный набор `[A,B]`, но итоговая база Pin **не совпадает** с первоначальной. Поэтому режим остаётся `RECALCULATED`, итог `A=34, B=66`, `DIRTY` — не `25/25`.

### 6.2. Детерминированный алгоритм перерасчёта (DESIGN на базе S2)

Вход: **упорядоченные активные привязки**, полный набор `pinned_shares` для всех известных привязок и режим `RECALCULATED`. Архивные/удалённые строки в математике не участвуют и отображаются как `0%`; их Pin сохраняются, но не резервируют доли до восстановления.

1. `fixed = sum(pinned_share для активных pinned)`.
2. `free = 100 - fixed`.
3. `n = количество активных unpinned`.
4. Если `n > 0` и `free > 0`: каждому незакреплённому назначить `base = free // n`; оставшиеся `free % n` единиц распределить по **стабильному порядку** активных офферов, по одной на строку.
5. Если `n == 0`: композиционное изменение допустимо только если `fixed == 100`.
6. Если `fixed > 100`, `free < 0`, `n > 0` при `free == 0` либо есть недопустимые нулевые/отрицательные доли, публикацию отклонить с понятной валидационной ошибкой. Также запрещено ноль активных офферов в редактируемом fallback-потоке.
7. Для `Pin` фиксировать **показанное текущее целочисленное значение** в момент принятого действия. Свободное изменение числа руками не требуется.

**Примеры из демонстрации и критериев:**

| Состояние | Ожидаемые значения |
|---|---|
| 3 одинаковых активных без Pin после пересчёта | `34 / 33 / 33` в стабильном порядке, сумма 100 (иной стабильный порядок остатка допустим) |
| Добавление четвёртого | `25 / 25 / 25 / 25` |
| Четыре активных → добавлен пятый | `20 / 20 / 20 / 20 / 20` |
| Закреплён один `25`, активны ещё два без Pin | `25 / 38 / 37` |
| В Keitaro после внешнего удаления фактически осталось `25 / 25`, затем `Fetch` | **`25 / 25`, без пересчёта** |
| В черновике `Remove(A)` | `A = Removed, 0`; активные доли пересчитаны с сохранением Pin |

Для `SNAPSHOT` вообще **не запускать** алгоритм 100%-ного распределения. Это правило отображения, не утверждение о вероятностях трафика. Канонический результат domain — **целые percentage points**; точное преобразование в поля Keitaro определяет только подтверждённый API mapping (§9). Не интерпретировать raw `share` как процент без проверки.

### 6.3. Один Python-алгоритм для Preview и Push

- Domain-функция **чистая, детерминированная, типизированная, без I/O**. Логический вход: `base_offers` (порядок + считанные значения), `base_pinned_shares`, `active_offer_ids` (порядок), `pinned_shares` (желаемое полное состояние), `mode`. Выход: валидированное состояние и список долей, `dirty`, ошибки ограничений.
- Важнейшее правило: при совпадении итоговых IDs **и** Pin с базой функция в любом режиме возвращает **исходные доли / SNAPSHOT / CLEAN**. В противном случае `SNAPSHOT` допустим **только при неизменном активном составе**; иначе вход невалиден. `RECALCULATED` всегда применяет §6.2.
- Для `Preview` браузер присылает базовые данные, желаемые значения Pin и режим; сервер проверяет диапазоны, уникальность и согласованность. Эти данные допустимы для расчёта без записи, но не доверяются при Push.
- Для `Push` сервер перечитывает действительные remote `base_offers` и локальные `base_pinned_shares`, сверяет их отпечатки с `base_revision` и `base_pin_revision`, затем вызывает **ту же domain-функцию с теми же логическими аргументами**. Клиентские цифры не являются источником истины.
- При неизменных подтверждённых базовых данных результат Push по составу и долям должен **строго совпадать с последним актуальным успешным Preview**. Нельзя перед Push без нового Preview менять режим, состав или Pin.
- Если меняются только Pin в `SNAPSHOT`, сохраняются только локальные настройки; считываемые `25/25` не нормализуются и upstream PUT не нужен. Если черновик уже в `RECALCULATED`, `Pin/Unpin` может менять доли и требовать upstream PUT.

### 6.4. Pin/Unpin и архив (DESIGN)

- `Pin` сохраняет текущий **отображаемый процент** для конкретной привязки `(campaign_id, stream_id, offer_id)`; в `RECALCULATED` пересчёт выполняется сразу. `Unpin` снимает закрепление: в `SNAPSHOT` без пересчёта, в `RECALCULATED` с пересчётом.
- Поля `base_pinned_shares` и `pinned_shares` используют **полную snapshot-семантику настроек**, не patch: это объекты только из записей с действующим Pin; **отсутствующий ключ означает Unpin**, а не «оставить без изменений». `{}` означает отсутствие закреплений **у всех ранее известных привязок данного потока и новых, ещё не опубликованных строк**, включая архивные. Для сохранения Pin архивной строки фронтенд обязан передавать её запись в полном наборе. Если новый staged-only оффер добавили, закрепили, а затем отменили добавление до Push, его Pin также исчезает из черновика; архивная запись не создаётся.
- У архивных строк Pin остаётся локальным, не входит в сумму `fixed` до `Bring Back`. Редактор позволяет снять конфликтующий Pin через `Unpin`.
- Для `dirty`, восстановления исходного snapshot и `Cancel` сравнивать итоговый Pin с **базовыми Pin**, полученными при Fetch/подтверждённом Push, а не только с текущими активными IDs.
- Если внешний пользователь изменил в Keitaro долю закреплённого оффера, Fetch показывает **фактическую** долю; сохранённый локальный Pin отображается отдельно как намерение, без принудительного upstream изменения, при несоответствии — предупреждение.
- После Push Pin-настройки считаются сохранёнными только при подтверждённом remote readback (или, для pin-only, после успешной локальной транзакции). При несовпадении remote значений с рассчитанными исход не подтверждён.

## 7. SQLAlchemy: локальная история и Pin

### 7.1. Назначение локальной БД

**REQ:** SQLAlchemy обязателен по S1. **DESIGN:** использовать его для предметных данных, которые Keitaro не сохраняет для нашего редактора: **ранее известные привязки, имена для архива и pin-настройки**.

Не делать локальный дубликат всех кампаний/потоков/офферов. Полноценный persistent operation journal и универсальная идемпотентность из v0.2 **не входят** в обязательную модель.

### 7.2. Таблица `known_offer_bindings` (проектная схема)

| Колонка | Тип/смысл |
|---|---|
| `campaign_id` | ID Keitaro, обязательный, часть составного уникального ключа |
| `stream_id` | ID Keitaro, обязательный, часть ключа |
| `offer_id` | ID Keitaro, обязательный, часть ключа |
| `offer_name` | Последнее подтверждённое имя, чтобы отображать архив даже после исчезновения из потока |
| `pinned_share` | Nullable integer 1..100 — наша локальная настройка закрепления |
| `last_seen_share` | Последняя фактически считанная доля (диагностическая историческая величина; **не** текущая правда) |
| `first_seen_at` | UTC, когда впервые успешно увидели привязку |
| `last_seen_at` | UTC последнего успешного Fetch/readback, где привязка присутствовала |
| `removed_at` | Nullable UTC, когда при успешной синхронизации установлено её отсутствие |

Уникальность `(campaign_id, stream_id, offer_id)` — принятая модель, пока контракт API не обнаружит допустимые повторные bindings; при обнаружении изменить схему **до написания бизнес-логики**, а не тихо терять строки.

### 7.3. Синхронизация при успешном Fetch

1. Получить из Keitaro **полный и валидный** список потоков/привязок выбранной кампании (с учётом pagination, если применимо).
2. В короткой локальной транзакции сделать upsert присутствующих привязок: обновить имя, `last_seen_share`, `last_seen_at`; `removed_at = NULL`; pin **не сбрасывать**.
3. Для ранее известных bindings **именно этого потока**, отсутствующих в успешном полном ответе, установить `removed_at` (сохранить имя/Pin).
4. Вернуть объединение актуальных (из Keitaro) и архивных (из БД) строк. Архивные — `Removed`, `0`, `Bring Back`.
5. Если upstream чтение или валидация не удались — **не менять архив**, вернуть ошибку, старое состояние браузера оставить без массовых «удалений».

На первом Fetch система знает только видимые Keitaro привязки: восстановить **неизвестную ранее** историю она не обязана. Archive переживает перезапуск приложения за счёт локальной БД.

### 7.4. Черновик, Push и Pin

- При Fetch сервер возвращает `base_pinned_shares` **для всего известного набора (включая архив)** и `base_pin_revision` — детерминированный отпечаток канонического перечня известных `offer_id` и их `pinned_share`. Для самого отпечатка не нужны новое поле БД или отдельный журнал; временные метки `last_seen` в него не включаются.
- Preview использует переданные базовые Pin только для расчёта; Push **повторно читает** актуальные Pin из БД и сверяет `base_pin_revision`. При обнаруженном расхождении — `409 CONFLICT`, без незаметного слияния и сброса чужих настроек. Это best-effort проверка, не атомарная гарантия многопользовательского доступа.

- **До Push:** staged-only добавления/удаления/Pin живут в браузере, не попадают в архив. Это предотвращает ложную историю после `Cancel`.
- **После подтверждённого Push:** зафиксировать актуально прочитанные bindings, отметить удалённые архивными и обновить pin-настройки в **короткой** DB-транзакции.
- Если удалённая запись подтверждена, но локальная транзакция провалилась, вернуть отдельное сообщение «Keitaro изменён, локальная синхронизация не подтверждена»; не делать второй слепой `PUT`, предложить `Fetch`.
- Никакие SQLAlchemy-транзакции не держатся открытыми на время HTTP-вызовов Keitaro.
- Сессия БД создаётся на запрос/use-case; нет общей глобальной `Session`.
- Структура реализуется SQLAlchemy 2.x + Alembic. `alembic upgrade head` работает на пустой БД и повторно без потери данных.

**СУБД (ENG/DESIGN):** локальный SQLite достаточно; README честно указывает ограничение на конкурентные записи. PostgreSQL и кластеризация не требуются.

## 8. Внутренние HTTP API Adrobot (проектный контракт)

Эндпоинты ниже — **наши** маршруты FastAPI, не Keitaro Admin API. Поля иллюстративны и могут быть адаптированы при реализации; их пользовательская семантика нормативна.

| Метод | Путь | Назначение / side effects |
|---|---|---|
| `GET` | `/` | Создатель кампаний / ссылки на редактор |
| `GET` | `/editor` | Страница редактора |
| `GET` | `/api/offers?query=...` | Поиск существующих офферов в Keitaro, только чтение |
| `GET` | `/api/reference-data` | Проверка/получение настроек домена, группы, источника, только чтение |
| `POST` | `/api/campaigns` | Создать кампанию с двумя потоками |
| `GET` | `/api/campaigns/{campaign_id}/editor` | Fetch потоков; **локальная синхронизация архива**, без remote write |
| `POST` | `/api/campaigns/{campaign_id}/streams/{stream_id}/preview` | Чистый пересчёт черновика без изменений БД/Keitaro |
| `PUT` | `/api/campaigns/{campaign_id}/streams/{stream_id}/offers` | Push желаемого состава и Pin, сравнение состояния, remote write/readback/локальный sync |
| `GET` | `/health` | Проверка работоспособности процесса, без мутации |

### 8.1. `Fetch` и `Preview` (не upstream JSON)

**`GET /editor` — HTML-страница**, а `GET /api/campaigns/{campaign_id}/editor` — JSON-Fetch, возвращающий для каждого потока базовый снимок: упорядоченные активные `offer_id` и считанные `displayed_share`, `base_revision`, архив, `base_pinned_shares` по **всем известным привязкам** и `base_pin_revision`. Браузер сохраняет эту базу до Cancel/подтверждённого Push. Стартовый режим `SNAPSHOT`.

`Preview` — stateless и **не читает Keitaro на каждом нажатии**. Браузер передаёт базовый snapshot вместе с полным желаемым составом/Pin и выбранным режимом:

```json
{
  "base_revision": "opaque-remote-hash",
  "base_pin_revision": "opaque-local-pin-hash",
  "base_offers": [
    {"offer_id": 3749, "displayed_share": 25},
    {"offer_id": 3717, "displayed_share": 25}
  ],
  "base_pinned_shares": {"3749": 25},
  "active_offer_ids": [3749, 3717, 3800],
  "pinned_shares": {"3749": 25},
  "mode": "RECALCULATED"
}
```

Оффер `3800` в этом примере ранее известен как архивный; остальные Pin отсутствуют. **Списки `pinned_shares` и `base_pinned_shares` — полный набор закреплений, а не набор изменений**: отсутствующий ключ означает `Unpin`; если у архивного оффера есть Pin и пользователь его не снимал, этот Pin обязан оставаться в `pinned_shares`. `null` не является отдельным значением «не менять».

`Preview` проверяет и возвращает нормализованное состояние: `active_offer_ids`, `pinned_shares`, `mode`, `offers` с целыми долями и статусами, `dirty`, `validation_error` и признаки актуальности. При недопустимом изменении UI сохраняет **последний валидный** черновик. Режим и `dirty` определяются по нормативным правилам §5–6, а не по пришедшим из браузера готовым процентам.

Вводимые `base_offers`/`base_pinned_shares` на `Preview` недоверенные, приемлемы только для нефиксирующего расчёта; `Push` сверяет **реальные** базы в Keitaro и БД.

### 8.2. `Push` и актуальность Preview (не upstream JSON)

```json
{
  "base_revision": "opaque-remote-hash",
  "base_pin_revision": "opaque-local-pin-hash",
  "active_offer_ids": [3749, 3717, 3800],
  "pinned_shares": {"3749": 25},
  "mode": "RECALCULATED"
}
```

- `base_revision` — обязательный отпечаток remote-снимка; `base_pin_revision` — обязательный отпечаток базового локального набора известных привязок и Pin. Сервер заново читает **обе** базы и проверяет их до mutating API вызова. При конфликте — `409` без remote write. Для полного сравнения исходного состава по модели §6.3 он использует прочитанный remote snapshot, а не client `base_offers`.
- `active_offer_ids` — упорядоченный список, `pinned_shares` — **полное** конечное состояние Pin всех известных привязок этого потока, включая архив. Отсутствующий ключ означает **снять Pin**; отсутствующий `pinned_shares` как поле — ошибка валидации, а не команда «ничего не менять». Неизвестные IDs, дубли и недопустимые значения проверяются сервером.
- `mode` — часть контракта (`SNAPSHOT` / `RECALCULATED`), а не производная только от конечных IDs. В режиме `SNAPSHOT` активный состав должен равняться базовому; одинаковые IDs с **изменёнными** Pin могут оставаться `RECALCULATED`, если ранее менялся состав. При полном совпадении IDs и Pin с базой применяется приоритет `SNAPSHOT / CLEAN` и запись не требуется.
- **UI сериализует Preview**: до завершения запроса действия и Push для этого черновика заблокированы. Для минимального интерфейса выбрана последовательная блокировка (не одновременные запросы); интерфейс хранит **точные канонические входные данные последнего успешного Preview и показанный ответ**. Любое изменение состава/Pin/режима инвалидирует его; Push разрешён только после получения успешного Preview именно для текущего черновика. Ошибка, отставший ответ или незавершённый Preview блокируют публикацию.
- Push **не хранит серверную историю Preview**: он перечитывает обе базы, проверяет их версии и повторно применяет ту же детерминированную domain-функцию к каноническим входам. Совпадение с показанным Preview обеспечивается неизменностью этих входов и контролем актуальности **в UI**, а не несуществующим серверным «последним Preview». При неизменных базах, порядке IDs, полном Pin и режиме результат Push обязан соответствовать показанному Preview; если readback отличается, нельзя объявлять SUCCESS. Прямой API-вызов, минующий UI, независимо валидируется, но не получает обещания сверки с историей предыдущих Preview.
- Если изменились только Pin и remote состав/доли совпадают с базой, допускается локальная запись без upstream PUT. Если доли в `RECALCULATED` изменились, соответствующий remote PUT необходим (после проверки API mapping).

### 8.3. Ошибки и типы результата

- Успешный ответ содержит данные readback (или, для pin-only, подтверждённые локальные настройки).
- Ошибки возвращаются машинно-читаемо: `error.code`, безопасное `message`, `request_id`; при частичном создании — известные ID и стадия; без upstream credentials/traceback.
- `Cancel` — локальное восстановление состояния браузера, без HTTP API.
- Блокировка повторного нажатия в UI дополняется серверной валидацией, но **не объявляется глобальной гарантией идемпотентности**.

## 9. Keitaro Admin API: интеграционный контракт и исследование

### 9.1. Что проверить на фактическом инстансе до live-записи

- Версию Keitaro и актуальный базовый путь Admin API; способ авторизации `Api-Key`.
- Поля кампании (name, domain, group, source, alias) и доступные default IDs.
- Получение офферов и поиска/списка с пагинацией.
- Получение кампании и **полного** списка потоков; распознавание offer vs redirect stream.
- Создание кампании, потоков, GEO-фильтра, redirect на Google и позиционного порядка.
- Получение и обновление состава привязок и значений доли/веса; семантику конкретных полей API (`share`, `weight` или иное).
- Минимальный безопасный набор изменяемых полей для update; какие атрибуты необходимо сохранять при read-modify-write.
- Возможность отключённой кампании при частичном создании (если имеется); отсутствие такой возможности не блокирует сдачу.
- Семантику пустого offer stream и дублирующихся `offer_id`.

**Артефакт исследования:** `docs/keitaro-api-notes.md` — короткая таблица *реально проверенных* endpoints, полей и особенностей инстанса, без API-ключей. Непроверенные примеры из внешней документации не выдаются за установленный контракт.

### 9.2. Требования к клиенту

- Отдельный `KeitaroClient`/adapter, используемый application services; роутеры и шаблоны не формируют raw-запросы Keitaro.
- Один конфигурируемый `httpx.AsyncClient` с переиспользованием соединений на lifespan, корректное закрытие.
- Ненулевые ограниченные connect/read/write/pool timeouts; корректная обработка `401/403`, `404`, `422`, `429`, `5xx`, невалидного JSON и сетевых ошибок.
- Типизированная проверка важнейших полей; отсутствие обязательного поля — **интеграционная ошибка**, не молчаливый пустой список.
- Upstream host фиксируется настройками сервера, не произвольным пользовательским URL; TLS verify включён.
- Автоповторы возможны для безопасных чтений с небольшим лимитом; **никаких автоматических повторов мутирующих операций с неизвестным исходом**.
- Update меняет только офферы/их доли нужного потока, сохраняя action, filters, redirects, position, landings и остальные нецелевые поля. Для full-object PUT нужно явно собирать payload из **свежего** снимка с сохранением неизвестных полей, если API позволяет.
- После remote write обязательны readback и проверка сохранённых ID/значений; HTTP 2xx сам по себе недостаточен.

### 9.3. Работа с тестовой средой

- Диагностику начать с read-only запросов.
- Write smoke только на специально созданных/выделенных тестовых кампаниях; не изменять чужие рабочие кампании.
- Не публиковать логин, пароль и API-ключ Keitaro в код, README, screenshots, CI или логи.
- Обычный pytest и CI никогда не обращаются к реальному Keitaro; live smoke — явная отдельная команда.

## 10. Ошибки, конфликты и гарантии

### 10.1. Классы ошибок

| Ситуация | Поведение |
|---|---|
| Пустое имя/неверное GEO/Offer ID | `422`, ничего не создавать |
| Кампания/поток/оффер не найдены | `404` либо `422` по смыслу; ясное сообщение |
| Список потоков/офферов прочитан не полностью | Integration error, не менять архив и UI на Removed |
| Нет прав, ключ невалиден | Адаптер отличает auth error; никаких секретов в ответе |
| Upstream timeout/ошибка сети на чтении | Запрошенные данные не обновлены; повтор чтения безопасен |
| Timeout после потенциальной записи | `UNKNOWN`: результат не подтверждён, **без автоповтора** |
| Кампания создана частично | `PARTIAL`: известные ID и стадия; без автоматического rollback |
| Успешный `PUT`, readback не совпал | `UNKNOWN`/«не подтверждено», нет ложного успеха |
| Нельзя распределить Pin | Валидационная ошибка Preview/Push, никаких remote write |
| Изменился целевой поток с последнего Fetch | `409 CONFLICT`, не писать поверх, сохранить черновик |
| БД не смогла сохранить архив после успешного Push | Сообщить, что Keitaro мог быть обновлён, локальная синхронизация не подтверждена; предложить Fetch |
| Удаление последнего активного оффера | Отклонить как DESIGN-ограничение до подтверждения поведения пустого fallback |

### 10.2. Защита от перезаписи чужих правок — явное DESIGN-решение

При `Fetch` формируются `base_revision` — хеш канонизированного remote-снимка **полей целевого потока, которые могут быть перезаписаны при обновлении**, и `base_pin_revision` — отпечаток известного локального состава Pin (§7.4). Перед `Push` сервер перечитывает Keitaro и локальные настройки и сравнивает обе базы. При расхождении — `409 CONFLICT`; UI предлагает `Fetch` и не удаляет черновик до подтверждения пользователя.

**Статус: обязательная для нашей реализации best-effort проверка, а не атомарная CAS-гарантия.** Без поддержки Keitaro условной записи сохраняется race между prewrite GET и PUT, как и возможные локальные гонки между проверкой Pin и фиксацией; это честно описывается в README. Нет отдельных «по возможности» и взаимоисключающих статусов `base_revision`.

### 10.3. Чего система не обещает

- Локальный `request_id`/UUID не обеспечивает дедупликацию удалённого `POST` создания кампании.
- Не предусмотрены автоматическое восстановление `RUNNING` после падения процесса и отдельная таблица с восемью статусами.
- Не предусмотрены фоновые compensating transactions и повторные `POST` при неопределённом исходе.
- Журналирование и readback не превращают Keitaro+SQLite в одну транзакцию.
- Не заявлены произвольные SLA/производительность/многопользовательская атомарность, которых заказчик не требует и которые не проверены.

## 11. Архитектура: компактный модульный монолит

### 11.1. Границы ответственности (ENG)

```text
Browser (Jinja2 + minimal JS):
    формы, список, локальный черновик/режим, сериализация Preview, кнопки
                     │ HTTP/JSON
FastAPI (routers + Pydantic):
    приём запроса, server validation, error mapping, сериализация
                     │
Application services:
    CreateCampaign / FetchEditor / PreviewEditor / PushOffers
                     │
   ┌─────────────────┴──────────────────┐
   ▼                                    ▼
Pure domain rules                 Infrastructure
composition, pins, math           Keitaro HTTP client + SQLAlchemy/Alembic
```

- UI не общается с Keitaro напрямую и не получает ключ.
- В FastAPI-роутерах **нет** сложной последовательности HTTP-запросов или математики офферов.
- Domain не зависит от FastAPI, SQLAlchemy, httpx, HTML/JS.
- Application service координирует чтение, вычисление и запись, знает только узкие интерфейсы/объекты инфраструктуры; `Protocol` вводить лишь там, где есть реальная подмена в тестах.
- БД хранит архив/Pin; клиент Keitaro хранит знания о его JSON, не domain.
- Один типизированный сценарий может быть обычной функцией; не вводить бессодержательные `BaseService`, универсальные RepositoryFactory/UnitOfWork/командные шины.
- Не создавать отдельный каталог/файл лишь ради «чистоты» диаграммы; структура определяется используемыми компонентами.

### 11.2. Предлагаемый компактный скелет

```text
adrobot/
├── src/adrobot/
│   ├── main.py                 # app factory, lifespan, wiring
│   ├── config.py               # typed settings
│   ├── api/                    # routes, schemas, error mapping
│   ├── services/               # create/fetch/preview/push use-cases
│   ├── domain/                 # models, state transitions, allocations
│   ├── keitaro/                # typed client, upstream DTO/payload mapping
│   ├── db/                     # SQLAlchemy model, session, archive access
│   └── web/                    # Jinja templates, CSS, JS
├── alembic/
├── tests/
│   ├── unit/
│   ├── contract/
│   ├── integration/
│   └── live/                   # opt-in only
├── docs/keitaro-api-notes.md
├── .github/workflows/ci.yml
├── .pre-commit-config.yaml
├── .env.example
├── pyproject.toml
├── uv.lock                    # либо другой зафиксированный lock
└── README.md
```

`Dockerfile`/`compose.yaml` — **опционально**; один действительно проверенный путь установки и запуска обязателен. Отдельные `architecture.md`, `data-model.md`, ADR не являются обязательными артефактами: краткая схема в README достаточна. Если сложная деталь требует пояснения, допустим один короткий дополнительный документ.

### 11.3. Асинхронность и ресурсы

- Для внешнего API выбрать `httpx.AsyncClient` и `async` orchestration.
- Для SQLite выбрать один последовательный подход SQLAlchemy (async с `aiosqlite` **либо** sync с короткими БД-вызовами без блокирования event loop). Выбор и способ работы с сессиями документировать.
- Нельзя переиспользовать одну SQLAlchemy Session конкурентно между запросами.
- Не держать DB transaction открытой на протяжении сетевого I/O.
- Нет фоновых задач/очередей, если функция не требует.

## 12. Безопасность, наблюдаемость, эксплуатация

### 12.1. Секреты и поверхность приложения (ENG)

- `.env` игнорируется Git; `.env.example` содержит исключительно плейсхолдеры.

- Приложение по умолчанию слушает `127.0.0.1`. Если публиковать в интернет, нужны отдельные меры авторизации, HTTPS и ограничения доступа; без них публичное размещение интерфейса с write API **не входит в задание**.
- Проверка git-истории и рабочей директории на секреты перед публикацией.

### 12.2. Логи и ошибки (ENG)

- Использовать стандартный Python `logging` со структурированными полями либо лёгкий JSON-formatter; логи в stdout.
- Существенные операции содержат `timestamp`, `level`, `request_id`, `action`, `stage`, ID кампании/потока (если известны), длительность и код ошибки; не нужен отдельный сложный trace stack.
- Прогнозируемые ошибки превращаются в безопасные читаемые ответы; неожиданные stack traces — только в серверном логе.
- `GET /health` не вызывает Keitaro и не делает запись.

### 12.3. README (обязательно)

README содержит назначение и две функции, версии Python, установку, переменные окружения, `alembic upgrade head`, запуск, тесты, pre-commit/CI, короткое описание архитектуры, модель архива, оба режима черновика и семантику Pin/Fetch/Preview/Push, порядок live-smoke на тестовой кампании, известные ограничения (`UNKNOWN`, race GET/PUT, непостоянный черновик) и правила обращения с секретами.

| Качество | Читаемые имена и небольшие функции, отсутствие оставленных `TODO` в обязательной логике, явно изложенные компромиссы |
| AI | Сгенерированный код и тесты проверяются теми же lint/type/tests и реальной API-семантикой |

**Нет обязательного числа 80% покрытия.** Покрытие можно публиковать для ориентира, но критерий приёмки — конкретные кейсы и отрицательные сценарии. Нет необходимости запускать полный pytest на каждый pre-commit; CI запускает всё. Никаких отдельного ADR-набора или второго обязательного способа деплоя только «ради солидности».

Рекомендуемая локальная последовательность:

```bash
uv sync --group dev
uv run pre-commit install
uv run pre-commit run --all-files
uv run ruff check .
uv run ruff format --check .
uv run mypy src/adrobot
uv run pytest
uv run alembic upgrade head
```

Инструмент `uv` — принятый ориентир; если выбран `pip` с зафиксированными зависимостями, README и CI должны использовать **один и тот же** способ. Примеры команд превращаются в фактические только после создания проекта.

| AC-E-11 | После внешнего удаления C,D и `Fetch` фактических `A=25/B=25` закрепить `A=25`, затем `Bring Back(C)` | В черновике `A=25`, `B=38`, `C=37`; закреплённые 25 сохранены |
| AC-E-12 | После AC-E-11 `Push` | Keitaro содержит A, B, C с подтверждёнными `25/38/37` в согласованном порядке; Pin сохранён локально |

| AC-E-14 | Недопустимая сумма закреплённых / нет свободных долей | Preview показывает ошибку, Push не пишет в Keitaro |

| AC-E-16 | Изменить только целевой offer stream | GEO-поток, остальные потоки и нецелевые поля сохранены |
| AC-E-17 | Целевой поток **или базовые локальные Pin** изменены с последнего Fetch | `409 CONFLICT`, без remote write и незаметной перезаписи чужих Pin; рекомендация перечитать |
| AC-E-18 | Ошибка записи или readback после Push | Нет ложного успеха, черновик сохранён, доступна безопасная повторная сверка |
| AC-E-19 | При Fetch `A25/B25` выполнить pin-only изменение в `SNAPSHOT` → Preview → Push | Показанные `25/25` не нормализуются, Pin сохраняется локально; лишнего upstream PUT нет; архивные Pin не теряются из-за пропущенных ключей |
| AC-E-20 | Возврат к исходным IDs **и** Pin, а также возврат только IDs при новом Pin; отмена/ошибка Preview | Полное совпадение восстанавливает исходные `25/25`, `SNAPSHOT/CLEAN`; совпадение одних IDs при новом `Pin(A34)` после композиционных изменений даёт `34/66` и `DIRTY`; старый/ошибочный Preview не разрешает Push, Cancel ничего не пишет |

## 15. План реализации на пять дней

Порядок — логический, без обещания будущих работ «в фоне». Приоритет всегда у воспроизведения двух пользовательских функций; качественные проверки подключаются с первого коммита.

| День | Инкремент с наблюдаемым результатом |
|---|---|
| **1** | Repo skeleton, настройки, Ruff/mypy/pre-commit/CI/Alembic; read-only исследование Keitaro, заполнение API mapping; первый рабочий `Fetch` через FastAPI/UI |
| **2** | Создатель кампаний: форма + application service + Keitaro client, live create на изолированной кампании, частичные/ошибочные кейсы |

| **4** | Push/readback, восстановление после опубликованного удаления, проверка remote/local base revision, актуальность Preview, ошибки интеграции; UI и live smoke |

Если фактический API окажется сложнее ожиданий, сокращать сначала декоративный UI, поиск кампаний, вторую конфигурацию запуска и отдельные документы. **Не сокращать** архив, Pin, Fetch semantics, безопасный Push и тесты математики.

## 17. Definition of Done — единый обязательный список

Работу можно считать готовой к сдаче, если **одновременно**:

- [ ] Создание кампании по Name/GEO/Offer ID подтверждено на выделенной кампании тестового Keitaro.
- [ ] У кампании два потока, правильные домен/группа/источник и порядок GEO → Google / fallback → Offer.
- [ ] Работают Fetch, Add, Remove, Bring Back **до и после Push**, Push, Cancel и Pin/Unpin.
- [ ] Внешнее удаление из Keitaro превращает ранее известную привязку в архивную только после успешного полного Fetch.
- [ ] Fetch не нормализует увиденные `25/25`; Preview считает активные доли и pinned-остаток правильно (`25/38/37`).
- [ ] Контракт `SNAPSHOT`/`RECALCULATED` выполняется: при одинаковых базовых данных, режиме, упорядоченном активном составе и полном наборе Pin результаты расчёта Preview и Push совпадают; `Unpin` в режиме перерасчёта обновляет доли; полное возвращение к базовым IDs **и** Pin восстанавливает CLEAN с исходными долями.
- [ ] Push сверяет remote `base_revision` и локальный `base_pin_revision`, повторно рассчитывает доли по тем же входам. UI допускает только текущий успешный Preview; при неизменных базах его значения совпадают с рассчитанными Push. Старый/ошибочный Preview не публикуется через UI.
- [ ] Архив и Pin сохраняются в SQLAlchemy, после подтверждённого Push выполняется readback.
- [ ] Не удаляются глобальные офферы, не изменяются нецелевые потоки и их поля.
- [ ] Неуспех, `PARTIAL`, `UNKNOWN` и `CONFLICT` не выдаются за успешный результат; нет слепых повторов мутаций.
- [ ] Есть автоматические тесты основных успешных и отрицательных сценариев, работающие без real Keitaro.
- [ ] Есть Alembic миграции, воспроизводимый запуск, `.env.example` и содержательный README.
- [ ] Выполняются Ruff, format check, `mypy`, pre-commit и GitHub Actions CI.
- [ ] В коде есть полезные типы/docstrings; ошибки диагностируются логами, секретов в репозитории и логах нет.
- [ ] Выполнены live smoke проверки на **выделенной** тестовой кампании.
- [ ] Фактические API-контракты **всех используемых операций из OPEN-01…06** (включая bindings, пустой stream, defaults и сохраняемые при update поля) зафиксированы в `docs/keitaro-api-notes.md`; отсутствие CAS и запрет последнего оффера допустимы как задокументированные ограничения.
- [ ] В итоговом README перечислены реальные ограничения (unknown result, отсутствие Keitaro CAS, временный draft, пределы SQLite) — без обещаний недоказанных гарантий.

**Не требуется:** Docker Compose, отдельная система оркестрации идемпотентности, 80% формального покрытия, обязательные ADR и восстановление незавершённого удалённого POST после падения процесса.
